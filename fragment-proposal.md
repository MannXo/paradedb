# Fragmented Release Artifacts

## Overview

This document outlines a new, automated workflow for managing SQL upgrade scripts and changelog entries. The current process is manual, requiring developers to edit version-specific files, which is prone to merge conflicts and complicates the cherry-picking process for stable releases.

The new design is based on the towncrier model, where each pull request contributes small, self-contained "fragment" files. These fragments are then automatically assembled into the final release artifacts at release time. This ensures that code changes, schema migrations, and changelog entries are treated as a single atomic unit, which simplifies development and release management.

## Problem

We currently construct SQL upgrade scripts manually on a PR-by-PR basis: in order to do that correctly, we need to anticipate which PRs will land on which branches, and which releases they will consequently be a part of. This has proven error-prone.

In order to more fully automate the construction of the SQL upgrade scripts, we should _also_ automate the changelog creation: that allows more of the release process to be executed in an automated fashion. This portion isn’t a blocking concern: more of a nice to have.

## Directory Structure

Two new directories will be created to store the fragments before a release:

| Path                        | Purpose                                      |
| --------------------------- | -------------------------------------------- |
| `pg_search/sql/unreleased`  | Contains unreleased SQL migration fragments. |
| `docs/changelog/unreleased` | Contains unreleased changelog fragments.     |

The existing `pg_search/sql` and `docs/changelog` directories will continue to hold the final, versioned artifacts generated by the release process.

## Developer Workflow

For each pull request that introduces a user-facing change or a schema modification, the developer will create one or more fragment files.

### SQL Fragments

- **Location:** `pg_search/sql/unreleased/`
- **Naming:** `<PR_NUMBER>.<short_description>.sql` (e.g., `1234.add_snippets.sql`)

### Changelog Fragments

To allow for automated generation of "flaired" release notes, changelog fragments will contain structured data in addition to the description.

- **Header Configuration:** A centralized file, `.changelog_headers.json`, will define a pre-approved list of changelog section headers. This file will map a simple keyword to the full Markdown header.

  _Example `.changelog_headers.json`:_

  ```json
  {
    "stability": "## Stability Improvements 💪",
    "features": "## New Features 🚀",
    "breaking": "## Breaking Changes 🚨"
  }
  ```

- **Fragment Structure:**
  - **Location:** `docs/changelog/unreleased/`
  - **Naming:** `<PR_NUMBER>.<category>.mdx` (e.g., `1234.bugfix.mdx`). The category helps with fallback behavior.
  - **Content:** The file will contain two parts:
    1. **Frontmatter:** YAML frontmatter specifying the `header` key chosen from `.changelog_headers.json`.
    2. **Description:** A brief, user-facing description of the change written in Markdown.

  _Example Fragment (`1234.bugfix.mdx`):_

  ```markdown
  ---
  header: stability
  ---

  Fixed an issue where blocks could get added to the free space map twice.
  ```

## PR Automation: SchemaBot Enhancement

The existing `SchemaBot` workflow (`.github/workflows/check-pg_search-schema-upgrade.yml`) will be enhanced to enforce the creation of SQL fragments.

1. **Detect Change:** The bot will generate a schema diff. This process will involve applying any SQL fragments present in `pg_search/sql/unreleased/` to the generated schema _before_ comparing it to the base schema. This ensures the diff accurately reflects the cumulative schema changes, including those introduced by the fragments.
2. **Enforce Fragment:** If a schema diff is detected, the bot will:
   - **Check for a corresponding fragment file** in `pg_search/sql/unreleased/` named `<PR_NUMBER>.*.sql`.
   - **If the file exists,** it will validate its content against the generated diff. If they don't match, the CI check will fail and instruct the developer to update the file.
   - **If the file does not exist,** the CI check will fail and the bot will comment on the PR with the expected file content and instructions on how to create it. This keeps the developer in control while using the bot for verification.

## Release Automation

The `publish-github-release.yml` workflow will be modified to orchestrate the fragment assembly process. The manual `confirmation` input will be removed. When triggered, the workflow will execute the following steps on the release branch (`main` or a stable branch like `0.19.x`):

### Assembly Scripts

Two new scripts will be created to handle the assembly:

1. **`scripts/assemble_sql.sh`**:
   - Finds all `.sql` files in `pg_search/sql/unreleased/`.
   - Sorts them numerically by their PR number prefix.
   - Concatenates them into a single new upgrade script: `pg_search/sql/pg_search--<previous-version>--<new-version>.sql`.
   - Uses `git rm` to delete the consumed SQL fragments.
2. **`scripts/assemble_changelog.sh`**:
   - Reads the available headers from `.changelog_headers.json`.
   - Finds all `.mdx` files in `docs/changelog/unreleased/`.
   - Groups the content of the fragments based on the `header` key in their frontmatter. If a `header` key is missing, it can fall back to a default based on the filename's category.
   - Creates a new versioned changelog file (`docs/changelog/<new-version>.mdx`), assembling the fragments under their corresponding "flaired" headers.
   - Uses `git rm` to delete the consumed changelog fragments.

### Workflow Steps

1. **Checkout:** The workflow checks out the code.
2. **Assemble:** It runs the `assemble_sql.sh` and `assemble_changelog.sh` scripts, providing the new version number.
3. **Commit:** It commits the newly created artifact files and the deletion of the fragments. This becomes the official "release commit".
4. **Tag and Publish:** It tags the release commit and proceeds with the rest of the publishing process.

## 6. Stable Releases and Cherry-Picking

This design is fully compatible with the existing process for stable releases.

- When a commit with fragments is cherry-picked from `main` to a stable branch, the fragment files are carried with it.
- The manual release preparation steps performed on the stable branch ensure that the `unreleased` directories on that branch accurately contain _only_ the fragments intended for the upcoming patch release.
- When the `publish-github-release.yml` workflow is run on the stable branch, the assembly scripts will correctly assemble all fragments present on that branch, creating the correct patch release artifacts. The deletion of fragments on one branch does not impact any other branch.
